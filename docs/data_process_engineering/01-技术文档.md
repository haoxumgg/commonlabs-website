> 仓库：`Reach/data_process_engineering`（Gitea）· 审阅版本：main（2026-07 代码包）
> 项目定位：飞书 RAG 问答机器人 1.0（企业知识库「万事通」），目标为可演示 Demo，一人开发。

## 1. 项目总览

本仓库是一套完整的**企业文档知识库 RAG 系统**，实现闭环：

> 飞书群里丢文档 → 自动下载入库（MinIO）→ 多格式转 Markdown → 清洗 → 切片 → 向量化（dense + BM25）→ 写入 Qdrant → 群里 @机器人提问 → 混合召回 + 精排 → LLM 生成带引用来源的回答 → 👍/👎 反馈闭环。

仓库由三部分组成：

| 目录 | 角色 | 规模 |
| --- | --- | --- |
| `rag/KnowledgeDataPipeline/` | 数据管线 + 召回 API 服务（FastAPI） | ~13k 行 Python |
| `rag/lark_message/` | 飞书机器人（长连接事件 + RAG 问答编排） | ~4k 行 Python |
| `rag/`（根目录散落文件） | 一次性运维/诊断脚本、知识源文档、演示页面 | 若干脚本 + 语料 |

### 1.1 技术栈

- **Web/API**：FastAPI + Uvicorn，Pydantic v2
- **对象存储**：MinIO（boto3 S3 兼容客户端，s3v4 签名）
- **向量库**：Qdrant（named vectors：`dense` 1024 维 COSINE + `bm25` sparse IDF）
- **结构化存储**：MySQL（SQLAlchemy 2.x async + aiomysql；当前主要为预留）
- **嵌入**：三后端可切换 —— 远程 OpenAI 兼容 `/embeddings`（DashScope `text-embedding-v3`）/ FlagEmbedding `BGEM3FlagModel` / transformers CLS pooling
- **稀疏向量**：fastembed `Qdrant/bm25`
- **精排**：BGE cross-encoder（本地 `bge-reranker-v2-m3`）或 DashScope rerank API（`qwen3-vl-rerank`）
- **文档转换**：MarkItDown、PyMuPDF、mammoth、python-pptx、openpyxl、PaddleOCR PP-StructureV3、LibreOffice + Poppler、豆包 VLM（`doubao-1-5-vision-pro`）
- **生成 LLM**：百炼 OpenAI 兼容接口（`deepseek-v4-pro`）
- **飞书**：lark-oapi SDK 长连接（WebSocket），OpenAPI 直调（urllib）
- **日志**：loguru + 结构化 JSONL 追踪（问答 / 召回 / 反馈）

## 2. 数据管线（KnowledgeDataPipeline）

### 2.1 存储布局（MinIO，桶 `knowledgebase`）

```
raw/<collection>/...           原始文件（如 raw/runbow_knowledgebase/lark/<chat_id>/<msg>/x.docx）
markdown/<相对路径>.md          转换产物（剥掉 raw/ 前缀，目录层级保留）
chunk/<相对路径>.json           切片产物（与 markdown 二级路径完全一致，仅换扩展名）
```

`utils/collection_router.py` 依 `raw/<collection>/` 第二段路径推断目标 Qdrant collection，白名单 `DEFAULT_COLLECTIONS`（`runbow_knowledgebase`、`rules`、`dictionary`、`cases`、`exceptions`、`company`、`templates`、`temporary`、`finance`、`hr`、`legal`），未识别回落 `temporary`。

### 2.2 三态机 + 断点续传

`orchestrator/knowledge_pipeline.py`（单文件全量管线，875 行）以本地 JSONL（`metadata/files_metadata.jsonl`）作为断点索引：

- 状态：`raw`（未处理/失败）→ `markdown`（已转 MD）→ `chunk`（已切片）
- 每个 `first_path`（源 key）取 JSONL 中**同 ETag 下状态 rank 最高**的记录；ETag 变化视为文件更新，重新走全流程但**复用旧 UUID** 串成审计链
- 续传规则：`chunk` 且 ETag 一致 → 跳过；`markdown` → 只补切片；其余 → 全流程
- 每步成功/失败都**立即追加一行 JSONL 并 flush**，抗中断
- CLI flags：`--force`、`--no-chunk`、`--chunk-strategy=`、`--no-pptx-visual`、`--source-prefix=` 等

**注意：仓库中存在第二套并行编排**（`orchestrator/pipeline_common.py` + `raw_to_markdown.py` + `markdown_to_chunk.py` + `chunk_to_qdrant.py` + `pipeline_stages.py`），把管线拆成三个独立 Stage 并新增第四态 `vectorized`，metadata 拆成三个 JSONL（`raw_to_markdown_metadata.jsonl` 等）。两套 metadata **互不相通**（`scripts/chunk_minio_to_qdrant.py` 的模块 docstring 自述"绕过两套管线 metadata 不互通的问题"）。详见 Review 报告 R-14。

### 2.3 文档 → Markdown 转换（`file_to_markdown/`）

统一入口 `unified_entry.convert_bytes(ext, content, filename, **kwargs)`，按扩展名路由：

| 格式 | 路径 | 说明 |
| --- | --- | --- |
| `.pdf` | `pdf_to_markdown.convert_pdf_bytes_unified` | 先检测扫描件（PyMuPDF 抽前 3 页文本判断）；文本型走 MarkItDown；扫描件分页渲染 PNG → OCR（默认最多 25 页） |
| `.docx` | `word_to_markdown.WordToMarkdownConverter` | mammoth → HTML → markdownify；ZIP 内 `word/media` 图片先 PP-Structure OCR，识别字符数 < 20 时 VLM「看图说话」兜底（豆包，限 300 字，禁总结/推断） |
| `.pptx/.ppt` | 视觉版 `pptx_visual_to_markdown.PptxVisualConverter`（默认） | LibreOffice → PDF → `pdftoppm` PNG（dpi 200）→ 每页 VLM 忠实转写；输出 `## <语义标题>` + `<!-- page: N -->` 溯源注释；任何失败自动回退 python-pptx 文本版并在 `metadata.visual_fallback_reason` 记录原因 |
| `.xlsx/.xls` | `structured_exporters.excel_bytes_to_markdown` | 每 Sheet 一段 `## Sheet: <name>`；表格转「字段名：值 字段名：值」每行一条 record 的纯文本（见 `table_renderer`，全角冒号、重名 header 加 `_2` 后缀） |
| 图片 | `image_to_markdown`（PP-StructureV3 单例，CPU） | 版面分析 + OCR，输出结构化 Markdown |
| `.json` | `json_to_markdown` | 层级转标题/列表 |
| `.md/.txt` | 管线内透传/包一层标题 | |

**统一收尾**：`markdown_postprocess.finalize_for_kb` —— 换行/零宽字符归一、NFC、残留 HTML 转 MD、残留 `| ... |` 管道表兜底转「字段：值」文本；随后进入 KB 清洗管线（下节）。表格统一为「字段：值」纯文本是全链路的刻意设计——避免 MD 表格被切片器逐行切碎。

VLM 调用集中在 `vlm_client.py`：`describe_image_with_retry` 按异常字符串区分瞬态错误（连接重置/5xx/超时）线性退避重试 2 次，401/403/结构异常立即放弃。

### 2.4 Markdown 清洗（`cleans/`）

`MarkdownCleaner`（dataclass，全开关可配）按**固定顺序**串 9 步，每步命中才写 `metadata`：

1. 跨页重复短行（页眉/页脚，需 `<!-- page: N -->` 或 `## Page N` 分页标记，≥3 页且出现率 ≥50%）
2. 页码行（`第 X 页`、`Page X of Y`、`- 12 -` 等整行匹配）
3. TOC 目录段（点状对齐 `....12` 与「目录标题 + 列表」两种模式，原始行可留档 metadata）
4. 结束/致谢/Q&A 行（`## 谢谢`、`THANK YOU`、`Q&A`，行长 ≤30 防误删）
5. 极短中文噪声行（有效中文 <8 字，保护标题/列表/表格/字段行）
6. 装饰横线（ASCII 与 Unicode 制表/块字符）
7. 空标题/空 bullet/空编号项
8. 整段精确去重（NFC + 折叠空白归一后 ≥2 次只留第一次；保护标题/页标记/短段）
9. 法律免责声明/版权模板（只扫尾部 5 段）

最后 `\n{3,} → \n\n` 兜底。附 `_smoke_test.py` 冒烟测试。整体质量较高，规则注释详尽。

### 2.5 切片（`chunker/`）

工厂 `ChunkerFactory` 注册四策略，默认取 YAML `chunker.default_strategy`（配置为 `markdown_structure`）：

- **text**：按 `\n\n` 段落贪心合并到 `chunk_size`
- **recursive**：分隔符序列 `["\n\n","\n","。",".", " ",""]` 递归切分
- **semantic**：行级启发式（标题边界 + 长度窗口 + 尾部 N 行 overlap）
- **markdown_structure**（主力，556 行）：先用 `DocTypeDetector` 判型（扩展名优先，其次内容特征：PPT slide 标记、表格密度、SOP 编号体系、中文多级标题编号），再分路：
  - `ppt`：按 `## Slide` / `---` 分页，提取 `page`/`slide` 元数据，`chunk_kind=page|slide`
  - `excel/sheet`：**每行 record 一个 chunk**（`chunk_kind=table_record`，带 `sheet`/`row_index`）
  - `word`：走 `utils/markdown_hierarchy.extract_sections`（markdown-it-py，正则兜底）取层级节点，**每 chunk 带 `breadcrumb`（祖先标题路径）与 `level`**；行内「字段：值」record 行单独成 chunk
  - `pdf`：有标题按标题切，否则句子边界切
  - `general/sop_report/structured_biz`：按配置的标题级别（`#`/`##`/`###`）切 section，超长再递归切；「Page N」等纯上下文标题并入邻近内容

切片后 `utils/chunk_dedup.deduplicate_document_chunks` 做文档内去重：精确哈希去重 + 「标题-only/超短 chunk 被后文包含」剔除 + 保守 LSH（`utils/lsh_deduplication.py`，datasketch MinHash，阈值 0.9、同 title 限定）近重去重，最后重排 index。

### 2.6 向量化入库（`chunk_to_qdrant` / `utils/`）

- **点 ID**：`uuid5(namespace, f"{doc_uuid}_{chunk_index}")` —— 幂等 upsert，重跑覆盖
- **payload 契约**（`utils/payload_builder.build_point_payload`）：`id`（`doc_uuid_chunk_index` 业务键）、`doc_uuid`、`chunk_index`、`content`、`token_count`、`source`、`markdown_key`、`filename`、`converter`、`chunker_strategy`、`doc_type`、`title`、`breadcrumb`（`A > B > C` 字符串）、`level`、`page`、`sheet`、`chunk_kind`、`record_index`/`row_index`/`part_index`、`tenant_id`、`tags`、`is_deleted`、`ext_info`（整个 chunk metadata 兜底入库）
- **向量**：named `dense`（批量调 EmbeddingClient，batch 32）+ `bm25` sparse（fastembed）
- **collection schema**（`db/qdrant.py ensure_collection_schema`）：dense COSINE 1024 + HNSW(m=16, ef=100)；sparse IDF modifier；payload 索引：`doc_uuid/tenant_id/source/filename/doc_type/chunk_kind/converter/chunker_strategy` KEYWORD、`is_deleted` BOOL、`content/title` TEXT（全文检索用）
- **删除**：`delete_by_doc_uuid` 默认软删（`is_deleted=true` set_payload），`--hard` 物理删；召回侧统一 `must_not is_deleted=true`

### 2.7 混合召回（`recall/`）

`HybridRecaller.search` 流程：

1. `QueryEncoder.encode`：dense（BGE query 模式带 Instruct 前缀；与入库同模型保证向量空间一致）+ BM25 sparse
2. `QdrantClient.hybrid_search`：dense + sparse 双 `Prefetch`（limit = max(候选数, 20)）→ **RRF 融合** `query_points`；统一带 `tenant_id` 过滤 + 软删过滤 + 业务过滤（`doc_uuid/doc_type/filename/tags`）
3. **并列全文检索补充**（`full_text_search`，默认开）：`content`/`title` payload TEXT 索引 `MatchTextAny`（OR 语义）scroll 拉候选（品牌词如 NIKE/Akzonobel 强匹配场景），与混合召回按 id 去重合并
4. **Cross-encoder 精排**（默认开）：`rerank_stage.apply_rerank` 对候选打分；`sensitivity ∈ {internal_discussion, personal_info}` 的片段分数 ×0.6 降权（配合 `tag_*.py` 打标脚本）；RRF 原始分保留在 `recall_score`
5. 后处理：`min_score` 过滤（精排开→`rerank.min_score`=0.68 实测校准；关→RRF 分阈值）、`max_hits_per_doc` 单文档限流、截断 `top_k`
6. **父子扩展**（parent_child，默认开）：对**最高分档**（`score ≥ top - 0.02`）命中，取 breadcrumb 去末段为父路径，scroll 同文档同父路径的兄弟 chunk（每组 ≤10 条，score 置 0 不参与排序），使「问第四层架构」能带出 L1~L5；合并后按 `(doc_uuid, chunk_index)` 恢复原文顺序
7. `recall_trace.record_recall_trace`：每次检索追加一行 JSONL（`logs/recall_trace.jsonl`，只记分数/定位不记 content；写盘失败绝不影响主流程）

Qdrant 调用统一 `_qdrant_retry` 包裹（5 次线性退避，应对共享服务器 502 抖动）。

## 3. 飞书机器人（lark_message）

### 3.1 事件流

```
飞书事件(WebSocket) → build_event_handler
  ├ im.message.receive_v1 → handle_message_event
  │    ├ message_id 去重（OrderedDict LRU 1000）
  │    └ 提交线程池(4 workers) _process_message
  │         ├ extract_qa_question:
  │         │    p2p 私聊 → 任意文本直接进问答
  │         │    群聊     → 必须 @机器人（递归收集 mentions 比对 bot_open_id）
  │         ├ 是问答 → handle_rag_question
  │         └ 非问答 → 转发企业服务器(可选) 或打印
  ├ card.action.trigger → handle_card_action（👍/👎 反馈落盘 + toast）
  └ bot_p2p_chat_entered → 空处理器吞噪声
```

`handle_rag_question`：取 tenant_token → 原消息贴「OK」表情（即时反馈）→ **帮助菜单拦截**（60+ 精确关键词 + 前缀）→ 组装 `RagQaService` → 回答 → 优先发带反馈按钮的交互卡片（失败退纯文本，引用回复挂在原提问下）→ `QaTrace` 全程记录落 `logs/qa_trace.jsonl`。

### 3.2 QA 编排（`app/qa.py RagQaService`）

1. **意图分流**：寒暄/自我介绍/感谢/过短输入整句匹配直接回复（不耗检索与 LLM）
2. **多轮改写**：有历史且（问题 ≤15 字或含指代词）时，一次 LLM 调用同时做「话题边界判断 + 指代消解」；新话题输出 `NEW_TOPIC:` 前缀→丢历史，追问→用补全后的查询且生成时带历史。会话存储 `conversation.py`：进程内 `chat_id:user_open_id` 键、3 轮、30 分钟 TTL、LRU 1000 会话、线程安全（接口设计为可平替 Redis）
3. **Aily 技能强路由**（可选）：关键词命中（新闻/动态/行业分析/BD 等）→ 强制调用对应 Aily Skill 拉外部分析，结果作为高价值上下文块
4. **召回**：HTTP 调 `/api/v1/rag/search`（5 次线性退避重试）
5. **柔性熔断**：rerank 最高分 < `RAG_MIN_RERANK_SCORE`(0.70) → 直接回「没检索到」，不投喂 LLM
6. **生成**：system prompt 为「平衡版」护栏（允许基于相关片段综合，无关则只输出 `[NO_ANSWER]` 标记）；user prompt 每片段带 breadcrumb 定位、截断 1800 字、刻意**不暴露 score**（父子扩展项 score=0 会被 LLM 误判）
7. **来源标注**：`SourceNameResolver` 把片段路径里的 `oc_*` chat_id / wiki token 实时调飞书 API 翻译成群名/文档名（进程级缓存），答案尾部列「引用来源」

### 3.3 文档入库侧

`download_group_files.py`：扫群消息（时间范围/分页）→ 下载消息附件 + 云文档；飞书 docx/wiki 直接取**原生 markdown**（`/docs/v1/content`），经 `feishu_markdown.py` 清洗（反斜杠+HTML 实体双重反转义、`<table>` HTML → MD 表格、合并单元格按最大列补齐）→ `MinioUploader` 上传 `raw/<collection>/lark/<chat_id>/<message_id>/<filename>`，接入主管线。

### 3.4 可观测性

- `observability.QaTrace`：trace_id、stage（success/recall_empty/no_answer/rag_fail/menu_intercepted...）、改写前后、召回命中数/top 分/来源、分阶段耗时（rewrite/recall/llm）、错误——一行 JSONL
- `feedback.py`：卡片按钮 value 带 trace_id + asker；任何群成员可点，按 (trace_id, user) 记录 is_asker，落 `qa_feedback.jsonl`
- `scripts/qa_stats.py`：离线统计报表
- 三处写盘全部遵循「记录绝不影响主流程」原则

### 3.5 Aily Webhook

`app/main.py` 内嵌第二个 FastAPI（`app_aily`），后台线程 `uvicorn 0.0.0.0:8080`，`POST /api/v1/aily/webhook {query}` 复用 RagQaService 无状态问答，供飞书 Aily 平台外挂调用。

## 6. 设计亮点（Review 正面结论）

1. **分层清晰**：converter→cleans→chunker→embedding→recall 每层单一职责，工厂 + 抽象基类接口统一，模块间通过 dataclass 契约解耦
2. **断点续传与幂等**：ETag + 状态机 + append-only JSONL + uuid5 点 ID，重跑安全
3. **降级链完备**：PPT 视觉版失败自动回退文本版并留原因；VLM/Qdrant/召回分级重试且区分瞬态错误；OCR 缺依赖不崩溃
4. **表格「字段：值」纯文本化**是贴合中文企业文档检索的务实选择，且源头+兜底双保险
5. **可观测性**：问答/召回/反馈三条 JSONL 追踪链靠 trace_id 关联，且严格「记录不影响主流程」
6. **中文文档字符串密度极高**，关键阈值都注明实测依据与调参指引，工程留痕意识好
7. 敏感内容治理有雏形：sensitivity 打标（可回滚脚本）+ rerank 降权，避开了改 collection 配置的风险路径

（存在的问题与整改建议见《02-代码Review报告.md》。）
